# 29. Destination Review System

Reviews will be **database-driven**, not hardcoded.

Each review contains:

```text
user_id
user_name
destination_id
rating
comment
review_date
created_at
```

### User Flow

```text
User visits destination
        ↓
Reads reviews
        ↓
Clicks "Write a Review"
        ↓
Checks authentication
        ↓
Selects 1–5 stars
        ↓
Writes comment
        ↓
Submit
        ↓
Backend validation
        ↓
MySQL
        ↓
Review appears on destination
```

### Authentication Rule

Logged-in user:

```text
Write a Review
```

Not logged in:

```text
Please login to write a review.
```

# 30. Dynamic Rating System

Eventually destination rating will be calculated from actual reviews.

Example:

```text
Reviews:
5 ⭐
5 ⭐
4 ⭐
5 ⭐
4 ⭐

Average = 4.6 ⭐
```

The system should eventually update:

```text
destinations.rating
destinations.total_reviews
```

based on actual destination reviews.

This prevents fake/static review counts from being used as the platform grows.


# 33. Destination Seed Strategy

The current TypeScript dataset contains:

```text
143 destinations
```

We should **not manually write 143 SQL INSERT statements**.

Instead:

```text
destinations.ts
      ↓
One-time seed/export process
      ↓
MySQL
```

Seed must be:

* Idempotent
* Re-runnable
* Duplicate-safe
* Slug-based
* Able to insert related images
* Able to insert highlights
* Able to insert activities
* Able to insert existing review data where available

### Important

`nearbyHotels` and `hotels` should **not** be inserted into destination tables yet because the Hotel system has not been created.

Hotel relationships will be implemented later when the accommodation database is ready.

# 34. Migration Numbering Rule

Migration numbering must remain sequential and unique.

Current destination migration:

```text
003_destinations.sql
```

Therefore, the older migration documentation referring to another:

```text
003 — Fix users + core tables
```

must **not reuse the same migration number**.

The migration history should be audited and renumbered/documented consistently before adding future migrations.

Future example:

```text
001_rbac_foundation.sql
002_migrate_existing_users.sql
003_destinations.sql
004_destination_seed.sql
005_hotels.sql
006_restaurants.sql
007_transportation.sql
...
```

Actual numbering should follow the migration files that exist in the repository.

# 50. Working Rule

## One Phase → One Feature → Test → Verify → Next

We will **not randomly jump between modules**.

For each feature:

```text
1. Inspect existing code
2. Design database structure
3. Create migration
4. Seed/test data
5. Build backend API
6. Test API
7. Connect frontend
8. Build UI
9. Test edge cases
10. Run production build
11. Fix errors
12. Mark feature complete
13. Move to next feature
```

### Important Rule

Existing working functionality should **not be unnecessarily rewritten**.

We will extend the current system and preserve working code wherever possible.
